\section{The End-to-End System}\label{sec:system}

UniPlan is a web application (\texttt{python3 main.py}). A student adds units and writes one sentence; the page writes what it read beside each clause and turns unsure clauses into two-option questions (Figure~\ref{fig:app}). Only after the student accepts or corrects these notes does the scheduler run, and the student then sees three weekly grids with one-line reasons.

	\caption{The web page on exam item e121 (AI-written). (a)~``No 9ams'' was read as a preference, so the page asks. (b)~After ``Can't'', the first pick and its reason.}

Each AI output has a limited job. Parsed conditions are a draft, binding only after the student confirms it; the ranking decides which timetables are shown first, never which exist; and the reasons come from the ranker's contributions, checked against the timetable. This is the Week~7 lecture's mixed-initiative pattern: the AI points out missing constraints, the person decides~\cite{engg2112_w07}. It degrades gracefully: if the GPU server does not answer, it uses the local model and then, within 15~s, the TF-IDF classifier (exam clause accuracy falls from \pRtwoC\% to \pLinC\%), and asks the student to check each condition.

\textbf{Deployment.} The run-time code is standard-library Python; the fine-tuned model runs in Ollama on one GPU. With the parser on one laptop GPU over the local network, a sentence for two to four units takes a median of \plMedianRec{}~s end to end (\plParseMedian{}~s of it parsing on the GPU server, about \plParsePerHour{} sentences an hour one at a time); enrolment opens for everyone at once, so a service would need queueing, untested here. A real deployment also needs an official feed or written permission from the university, seat numbers refreshed near enrolment day, and a real-student pilot (Section~\ref{sec:recs}). The natural operator is the timetabling office, which holds the feed and seat numbers; the main cost, one GPU per enrolment period, is not estimated.
